# Paired Starsector scenarios

Status: all actual game scenarios are **unmeasured**. No reference save was inspected, copied, loaded or published. No mod was removed and no launcher flag was changed. The following is the experiment contract for a future explicitly owned, disposable campaign harness; it is not evidence that a run occurred.

1. Select a disposable representative late-game checkpoint locally. Record its private SHA-256, runtime manifest, configuration, hardware/OS, launch entry point and live JVM flags. Keep the save itself private. Identify the actual campaign thread and a verified whole-frame timing seam; `advance(float)` reports game time and is not sufficient. Runtime/provenance inventory is not a complete content admission digest.
2. Keep the same save, scene, camera, speed/pause policy, runtime/mod set and warm-up/duration across paired runs. Start with 60 seconds of warm-up followed by a 120-second measurement window. Record speed changes, pause/menu/combat state and scenario deviations; segment or reject a run when these differ. Frame events must continue through known long frames and boundary guard intervals.
3. First compare frame-only collection with frame+JFR (`instrumentation-off` against `baseline`) to expose instrumentation overhead. Measure collector CPU/RSS, allocation, buffer pressure and drops too. Never assume an overhead percentage from another JVM or workload.
4. Run at least three matched repetitions of the reference `baseline`, an explicitly supported Strategic-AI-disabled `control`, and `shadow`; randomize or alternate their order and restore the same starting checkpoint before every repeat. A control must use a seam proven safe for that save and disable precisely the measured Java decision domain. Do not uninstall a mod or delete its saved objects to manufacture a fast control. A version flag or source method alone is not supporting runtime evidence. If there is no safe control seam, record the control as unavailable.
5. Add one certified `offload`, then `parallel`, only after G1/G2 and safe handover pass. Include capture, IPC, encoding, validation, apply, queueing and contention in the end-to-end observation. Shadow intentionally duplicates work and is not an acceleration benchmark. Record exact control/config differences in the control evidence and both manifests; other unexplained config differences reject comparison.
6. Align frame/JFR/node records with run/request/frame IDs, epoch anchors and uncertainty. Compare start/end clock anchors and reject jumps. Record thread CPU deltas, execution/wait/I/O observations, allocation sampling, GC pauses, queue peaks, stale rejections, process CPU/RSS/network counters and separate save/load spans. Use `analyze` and `compare` on sanitized exports; investigate private stacks locally when a cause remains ambiguous.

A JFR session should use its configured profile, an explicit duration and maximum recording size (initial 120 seconds, 64 MiB). Its raw binary may contain private paths, names and properties. `ExportRecording` strips these rather than copying arbitrary fields. Oracle documents [recording limits/settings](https://docs.oracle.com/en/java/javase/17/docs/api/jdk.jfr/jdk/jfr/Recording.html) and [event start/duration inspection](https://docs.oracle.com/en/java/javase/17/docs/api/jdk.jfr/jdk/jfr/consumer/RecordedEvent.html). These describe available APIs, not measured game compatibility or overhead.

This session has no qualified native game UI/process lifecycle harness. It therefore does not launch or attach to the user's existing game. A future live capture requires explicit ownership of the exact game process/tree, bounded cancellation, safe disposable checkpoint handling and campaign/frame-hook evidence from the [runtime experiments](../runtime/feasibility.md). Follow the [debugging guide](../starsector-debugging.md), including script-classloader restrictions, paused UI/screenshot behavior and log rotation. Missing real-game measurements remain a blocker for issue #12 closure.
