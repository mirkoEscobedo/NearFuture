## One owner and explicit construction

The new PortalServer or PortalClient owns exactly one ReceiptRepo by value, three private Swarms, and fixed connection/session/operation state. Each process opens its existing Store once before transferring ownership to ReceiptRepo::open_owned. Server and client each need their own already admitted local durable membership; a downloaded server policy cannot bootstrap the client. No handler, broker, codec, queued task or bulk state owns or opens another database. ReceiptRepo owns the existing PrivateVault, loaded TransportIdentity, local public identity and device signer. Store1 and book metadata remain distinct; no MiniatureStore/profile2 route is introduced.

Proposed owner-facing API, with exact state-machine method names settled only after effect freeze:

```rust
pub struct PortalServer { /* private repo, three Swarms, fixed state */ }
pub struct PortalClient { /* same ownership, one selected book original */ }
impl PortalServer {
    pub fn new(repo: ReceiptRepo, config: PortalListenConfig)
        -> Result<Self, PeerError>;
    pub async fn next(&mut self) -> Result<PortalEvent, PeerError>;
    pub async fn shutdown(&mut self) -> Result<(), PeerError>;
}
impl PortalClient {
    pub fn new(repo: ReceiptRepo, config: PortalWatchConfig, slot: u8)
        -> Result<Self, PeerError>;
    pub async fn next(&mut self) -> Result<PortalEvent, PeerError>;
    pub async fn shutdown(&mut self) -> Result<(), PeerError>;
}
```

Constructors consume a repo rather than a database path, raw key, supplied MembershipState, mutable Store closure or claimed authentication flag. Configuration is trusted local input, validated against repo.config()/local_public() and the recovered original. It never becomes a current-policy certificate. No live session, proof, challenge or permission is restored from it. A PortalEvent is an owned public observation: actual three-listener Ready, Progress, bounded lane Offline/refusal, an opaque digest verification, a persisted admitted receipt, or an updated public book anchor. It has no conversion to DurableAck, strategic intent, World or native projection.

ReceiptRepo currently proposes/implements open_owned(Store, PrivateVault, ReceiptConfig, &[BookAnchor]), local_public(), config(), recover_observations(), book_anchors(), original_for_slot(), initialize_originals(), and crate-private transport()/with_current_read()/selector/observe_selector/admit_remote_selector. These are moving API facts rather than acceptance of their source. Portal integration must use their final independently reviewed signatures. Constructors recover the full64-name reserved inventory before starting network-operation timers. serve uses no local receipt slots and refuses any present reserved root/tail; watch requires a configured existing original plus externally supplied anchor/minima. Failure never substitutes empty history or creates a missing book.

The repo's existing crate-private transport() returns an opaque borrow of its one loaded TransportIdentity. Portal construction uses that borrow transiently for the three fixed builders. The Noise key clones required by maintained Swarm construction occur only inside identity.rs. The portal does not load identity again, clone account/device seeds, extract raw transport keys, obtain a vault path getter, or move signer references into async work.

## Actual connection and current-policy cuts

Portal has its own closed Receipt/Bulk/Notification owner-slot enum; a wire lane byte cannot choose it. Swarm events supply the actual PeerId and ConnectionId. Each lane stores at most one connection record with private owner-instance generation, opened/deadline Instants, selected limits, current application state and exact pending backend request IDs. No unbounded completed-ID map or unauthenticated connection history is retained. A second established connection is closed; a closure/failure event clears state only if its actual tuple matches that lane's owned connection. Backend limits also cap pending negotiation before application admission.

Before every handshake proof, operation proof, hint admission, Ack, bulk progress/final receipt and queued response send/flush, the owner obtains a new synchronous repo.with_current_read cut. This reloads and validates actual SQL membership/known frontiers/local device identity. No await, arbitrary callback, book initialization, local mutation or Swarm polling occurs inside that signer/policy borrow. State machines verify both endpoint PLAYER roles, exact principal/device/peer mapping, current server-owner pin, scope/ruleset/content and unchanged session membership revision. A configured numeric minimum alone grants nothing. A policy revision change fences all affected lanes, including queued signed bytes with unchanged numeric request status. Public decoded NotifySelector is untrusted; only the state machine's freshly checked actual connection produces the private remote principal used by repo.admit_remote_selector.

The server requires its actual local peer/account/device to equal the pin and current membership owner. The client independently pins that tuple at every protected stage. Notification/client receipt expectations derive from the recovered OriginalReceipt with original request/account/device/scope/kind/payload_digest and computed133-byte RequestBinding digest. Incoming status/digest/notice cannot become a new expectation. Receipt operation acceptance must enforce exact expected operation/binding/original principal, current membership/minima, historical commit sequence<=source current EventSeq, valid signed exact prefix and one-use pending state. The pure ReceiptSession envelope guard is insufficient by itself.

A mismatched/expired/duplicate first protected attempt consumes its private state before validation according to the reviewed receipt/notification effects. Outbound errors report uncertainty or Offline/Pending; they never resubmit a strategic intent. Connection recovery creates fresh session/nonces and discards old subscription/sequence/permits. The first CLI slice uses explicit new watch invocation for reconnect; no unbounded automatic reconnect loop or restored active state exists.

## Request-response ownership and queue accounting

The pinned libp2p-request-response0.30.0 Event::Message carries peer, connection_id and an inbound or outbound request ID. ResponseSent carries the exact inbound ID and documents that the response was flushed. InboundFailure/OutboundFailure also carry actual connection and matching ID. These maintained source APIs suffice for ownership; no guessed numeric ordering or cross-Swarm ID equality is used.

Each lane owns a non-Clone reservation keyed by owner-instance, actual connection, direction and the corresponding typed backend request ID. At most one request is awaited on each lane, counting either direction. Control and bulk operations are client-initiated. Notification setup is client-initiated; server Notice is forbidden until Subscribed has the matching ResponseSent event and its response permit has been released. An unsolicited request while the lane is occupied refuses/closes that lane and cannot release or replace its outstanding permit.

Reserve exact encoded body bytes/items before send_request/send_response or queue insertion, with framing+4 charged separately. Immutable pending bytes remain charged while backend delivery is outstanding. A returned outbound response is taken only for its exact expected ID/peer/connection; its protocol state consumes/validates the attempt, then releases that owned request permit or invalidates the lane. A matching ResponseSent releases only its inbound response permit after fresh policy/epoch checking. InboundFailure, OutboundFailure and connection invalidation clear only that exact lane's owned entries. A stale/unmatched ID never frees another reservation. Failed send_response returns its owned record; no successful flush is inferred from enqueue.

Notification's pending Notice stays immutable until its first Ack attempt, owned failure or expiry. Ack acceptance also requires the exact Notice prefix digest and freshly checked subscriber; it releases only that Notice's matching ticket. NoticeAck never calls repo receipt persistence, Store::ack_outbox or any strategic acknowledgement. Broker/subscriber effect modules should own their private permits and expose named checked transitions; the portal must not invent public permit-forging or manual phase setters to drive them.

Hard per-direction encoded-body ceilings remain control65536/16 items, bulk131072/4, notification16384/16: total212992 bytes/36 items plus144 framing bytes at the generic full ceiling. Negotiation only lowers these ceilings. One awaited request per lane and one notification dirty marker are tighter reachable application limits, not extra queues outside accounting. Incoming/default parser bytes, typed fixed records, challenge state, Noise/Yamux/SQLite/private-book memory are distinct residuals.

## One rotating poll round

Use futures polling of the three owned Swarms rather than an unlimited biased select/drain. A poll_round attempts one ready application event from each lane in rotating order, handles at most three such events, sweeps all private deadlines and current-policy invalidation, then yields. Advance the first lane each round. If none is ready, register all three Swarm wakers and a bounded timer for the nearest deadline/25ms scheduling sweep. Do not busy-loop, accumulate a Vec of historical events, or recursively drain a ready notification stream. Maintained internal parsing/event work still has its separate fixed backend bounds; this is not a hard CPU scheduling proof.

Sweep before and after synchronous protected work. Pending Noise/application setup, operation challenge, request/awaited delivery expire5s; notification lifetime and unsent-marker5s rules remain exact. The foreground run has its own private deadline, independent of protocol expiry. Its500..60000ms duration starts before listen/dial and is never restarted at Ready, handshake completion, subscription or later query; network setup consumes the same finite run. The backend61s idle therefore cannot shorten a still-valid within-run late query. Accepted active ReceiptSession::admit_record/check_record does not call handshake fresh(); send/receive do. Accepted ClientSession/ServerSession::binding has no wall-clock active lifetime; BulkServer/Client methods apply5s fresh_time to each pending/active transfer creation Instant, not authenticated session age. These inspected APIs permit a new transfer/query later in the same unchanged-policy active session without changing their existing expiry logic. Checked time arithmetic/backward observations fail closed. The broker's one selector is observed at most once per100ms, with next due based on current monotonic time rather than a catch-up loop. SQL observation compares actual retained projection only; unrelated StoreRevision/outbox activity cannot create terminal hints. Notice token bucket/rate/coalescing rules stay inside reviewed notification effects.

A successful subscription always schedules one fresh receipt query. Valid Notice admission records one dirty generation and Ack, never a receipt. Query start captures that generation and immutable original; its completion clears only covered dirtiness. A later Notice leaves one follow-up query. Every query uses fresh receipt proof/session/current remote minima and repo.accept_verified before reporting an admitted public receipt. Unknown/Pending/refusal never grants permission to recreate or execute an intent.

ACL/SQLite/crypto/book work is synchronous headless owner work. Readiness/recovery happens before network timers; receipt append can still stall this owner, and polling cannot preempt OS sync or an ACL helper. Recheck foreground/operation deadlines and policy after returning before queued network publication. Failures may retain a valid already written observational prefix but cannot invent a fresh result. No5s response, game-frame p99 or hard realtime guarantee follows from rotating polls. Actual three-lane progress while book work/flood is active is required before reporting bounded observed responsiveness.

## Book configuration and explicit offline initialization

Keep two kinds of minima separate. Local KnownFrontiers(scope,event_sequence,store_revision,membership_revision) admits the existing local Store::open_existing. Remote SourceMinima(event,store_revision,membership_revision) belongs to each OriginalReceipt/BookAnchor and admits a signed source observation. A remote event/store minimum never becomes a local database-open frontier; no remote canonical state is imported. Membership minima can conservatively combine at the protocol boundary, but scope/current local policy must independently validate.

The concrete root-owned [portal-config-format.md](portal-config-format.md) settles exact ordered ASCII mode/field/row grammar for this design; independent scoped design R1 passed before parser source dispatch. Its source admission requirements and later reviewed revisions are authoritative over the outline here. Proposed trusted config parser is separate NF-PORTAL-CONFIG-1, with a regular-file read bounded to16384 bytes before decode, UTF8/lowercase fixed-width hex/canonical decimal, exact allowed fields and no unknown/duplicate/trailing fields. It accepts at most8 distinct slots0..7 and generations0..7. Common fields are universe/history/ruleset/content/local_account/local_device/local_event_min/local_store_min/local_membership_min/server_peer/server_account/server_device/server_membership_min. Canonical PeerId parsing must round-trip; numeric overflow, zero identity, unsupported kind or inconsistent scope/pin refuses before repo construction.

serve adds three explicit listen addresses and anchor_count=0. watch adds receipt_address/bulk_address/notification_address, anchor_count1..8 and fixed original-anchor rows. Each anchor row supplies slot/generation/head_digest/request/operation/original_kind/payload_digest/remote_event_min/remote_store_min/remote_membership_min. Original account/device/scope and source pin derive from the trusted common fields; RequestBinding digest is computed, never accepted as a caller override. The chosen watch slot must exist. Exact positional/field grammar and all argv/read/path bounds need source review before coding; no JSON/Serde/dependency addition is needed. Path argv is bounded/validated and never echoed in diagnostics.

Root chose a separate future offline init-book mode. It consumes existing identity/membership/Store and trusted typed originals/configured pin/context/minima/slot, requires the entire64-name reserved inventory absent, and calls reviewed repo.initialize_originals. It creates only immutable479-byte generation0 observational book records, with no generated request/op IDs, networking, strategic Store write, role grant or key creation. Its original rows are equivalent to watch rows without generation/head, initially1..8 roots. Normal serve/watch never initializes. A failed partial initialization remains a fail-closed artifact requiring explicit owned repair; it cannot silently finish, delete, relabel or reset.

Return public exact head anchors after successful init/append for independent trusted retention. Config/printed stdout/file beside the same book does not itself protect backup rollback. The operator or separately reviewed trusted external component supplies and retains inventory/head anchors and remote minima. If that external retention is absent, report the exact last-known observational view and explicitly omit rollback-protection claims. No wire-supplied anchor, saved proof or book checksum initializes a grant. Every open/recovery reads all64 reserved names, including unconfigured roots and corrupt later tails, through the reviewed bounded batch seam; partial scan summaries are discarded. An anchored older valid backup refuses rather than becoming a new empty book.

## Foreground CLI and shutdown

Proposed separate target nf-portal has finite serve/watch duration500..60000ms and explicit offline init-book. Its exact positional commands are `nf-portal serve VAULT SAVE_ROOT DB CONFIG DURATION_MS`, `nf-portal watch VAULT SAVE_ROOT DB CONFIG SLOT DURATION_MS`, and `nf-portal init-book VAULT SAVE_ROOT DB CONFIG`; unknown modes/options, surplus/missing args and invalid canonical numbers refuse before opening state. All modes open existing vault/save root/config/Store only; missing/corrupt keys or policy refuse. They introduce no key generation, authority claim, membership import, history fork, sync/install, daemon/service, process-name kill, GUI/game launch or strategic commit command. init-book has no listeners; serve announces Ready only after three actual NewListenAddr events. watch dials all three exact pins, independently authenticates each lane, selects one retained original, subscribes and fresh-queries. Optional bounded opaque bulk input is explicitly configured/test-owned; its result remains only total/digest verification.

CLI emits bounded public readiness/final status/anchor/digest summaries and static error classes, without per-record flood logs, private paths, keys or raw bodies. Owned process tests drain stdout/stderr continuously with finite caps and readiness deadlines. Headless CLI duration and owned-child test deadlines are separate; an unresponsive caller output sink is not native responsiveness evidence. No command reads a mutable Store from peer JSON or callback.

Shutdown stops new dirty triggers/queries, invalidates all three application states, discards exact owned ephemeral permits and asks each Swarm to close its actual ConnectionId. Poll maintained close progress fairly within a separate finite cleanup deadline; then drop only owned Swarms/repo. No partial receipt becomes DurableAck. Tests retain exact process handles, kill/reap every error path and run children under package Windows Job Object/hosted Linux supervision. Private filesystem/helper lifecycle remains owned by identity. No detached network task or signer worker is created.
