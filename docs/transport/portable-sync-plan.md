## Verified starting seams

NF-PEER-1 has two physical TCP/Noise/Yamux lanes, current durable membership at every protected stage, exact actual PeerId/ConnectionId binding, one-use5s challenges, signed reply prefixes and bounded application queues. It queries retained Unknown/Pending/Rejected. A successful retained kernel outcome returns KernelOutcome Unsupported. Bulk verifies only opaque ordered bytes; it neither retains a complete document nor installs one. HistorySync, SnapshotInstall and PubSub remain Unsupported. Required bits1/2 mean only retained query/opaque digest verification. The public foundation/Java schema1 probe registry and kernel domain7 stay closed.

Accepted `Store::query_bound` returns exact retained binding/status for its authenticated principal/device/scope. `Store::snapshot()` returns immutable Store1 bytes/digest/revision; `known_frontiers()` supplies event/store/member minima. The snapshot omits the separate membership table and exposes neither a complete authenticated checkpoint/log-head descriptor nor public history-export/import APIs. Private recovery validates the local hash chain and bounded256-entry journal tail. `MembershipRepository` exposes current validated public state/CAS; no signed membership-transition archive or automatic remote policy import exists.

The pending-acceptance MiniatureStore offers exact Store2 snapshot bytes, known event/store/member/authority minima and original intent/status. Its runtime claims/tickets/activity never belong in a downloaded grant. Accepted transport owns a profile1 Store; integrating profile2 requires an explicit one-owner repository refactor after issue36 acceptance. It cannot open a second Store beside an existing owner. Roles REPLICA/ARCHIVE already exist, but current `ProtectedOperation` recognizes Economic/Chat/Administration/Worker only; replica authorization must be an explicit reviewed policy seam.

## Phase A: explicit committed receipt and reconnect

Keep NF-PEER-1 unchanged. Propose `/nearfuture/peer/control/2` with an independently reviewed closed receipt capability and new domain-separated proof transcript. The minimum new receipt has profile/schema, scope/policy, RequestId, OperationId, exact retained binding digest, terminal phase and EventSequence. A CommittedReceipt means the named Store profile retained rejection=None after its durable transaction. It carries no opaque kernel payload, native effect, spendable projection or new permission. Unknown profile/outcome semantics remain Unsupported. If callers need actual typed outcome payloads, register those named Rust records first; foundation/Java IPC promotion remains a separate parity task.

A foreground reconnect owner persists bounded pending request bindings through the sole local repository. On disconnect it reports Offline/Pending; it does not invent success or advance a local canonical branch. Reconnect loads the same actual transport/device identity, authenticates a fresh connection/session and queries the original RequestId. Same ID/changed payload or principal conflicts. Old proofs, responses and minimum-frontier fields cannot migrate into the new session. A valid receipt cannot be shown for another request, scope, device, binding or current server policy.

Meaningful first slice: a real server-owned operation commits through the accepted storage owner, loses its reply, restarts, and two real encrypted peers query the exact retained terminal receipt repeatedly without another debit/event. Adversarial raw records cover duplicate/reordered/stale-session receipts and current server revocation while numeric status is unchanged. This proves committed-status recovery; it does not prove duplicate remote command delivery while mutating network commands remain unsupported. Any later command route must enter the same durable RequestId binding/idempotency port rather than rebuild an intent after reconnect.

## Phase B: bounded application publish/subscribe hints

Recommended first slice: implement actual subscribe/publish delivery over a separate maintained libp2p request-response notification protocol and physical lane. No dependency addition is needed. This is an explicit two-peer broker, without gossip forwarding, multicast or discovery. Subscription requires a fresh one-use authenticated operation and binds actual peer/connection/session, topic, scope, principal/device, current membership and minimum frontier. Only the pinned server can publish to that active subscription. A closed initial topic is RequestReceiptAvailable for requests bound to that subscriber; no hidden world state or private assets are broadcast.

A notice is a bounded dirty hint, never a canonical receipt or acknowledgement. The receiver rechecks current direct peer/session/membership, strict subscription sequence and bounds, then schedules a fresh protected query. Every authoritative status still uses PhaseA's fresh one-use proof. NoticeAck means bounded hint admission only; it cannot invoke Store outbox-delivery metadata or acknowledge a strategic transaction. Reconnect discards subscription sequence/queued hints and re-queries known pending requests. Notification loss, duplicate delivery, coalescing and expiry cannot change canonical state.

Proposed hard envelope: body<=1024 bytes, one topic/subscription per active peer, <=16 queued notices and <=16KiB encoded bodies per direction, one awaited notification delivery,5s delivery expiry, <=8 admitted notices/s with burst8. Coalesce only hints for the same request under the same subscription; never coalesce a transaction or authenticated terminal status. A dedicated lane/queue and bounded owner poll schedule prevent a flood from consuming control/bulk reservations. Extending two to three physical lanes must explicitly revise total connection/parser accounting and retained maintained Yamux transient<=1MiB per physical connection. These are proposed caps, not measurements or total RSS promises.

If maintained Gossipsub is specifically required, approve a separate feature/dependency/resource slice first. Cached libp2p0.57.0 declares gossipsub0.50.0; the scout lock resolves that exact version, while the current root lock has no gossipsub entry. Actual cached config APIs expose strict validation, manual application validation, transmit/RPC/control/handler queue bounds, topic filters and duplicate-cache duration. Time-limited message caches do not establish a hard cardinality/heap bound under unique-message flood; application rejection occurs after some backend admission. Enabling the feature is not enough to claim the proposed quotas. Audit and test backend ingress/cache limits before promotion, preserve accepted lock pins incrementally, disable partial messages/compression, and retain explicit addresses. Neither maintained gossip signatures nor Noise identity independently grant account/membership authority. A multi-peer gossip forwarding policy requires a separately reviewed author/receiver authorization model; it is excluded from the first broker slice.

## Phase C: authenticated missing-history export

Approve a dedicated Rust-only `/nearfuture/peer/sync/1` registry before coding, with exact supported kernel/store profiles and compiled implementation hashes. Suggested closed data records are SyncRequest, SyncManifest, JournalSegment, SnapshotDocument and ReplicaInstallReceipt; exact widths/transcripts and independent raw vectors must freeze first. This does not enlarge foundation SchemaPayload1 or make an arbitrary domain7 blob admissible.

SyncRequest binds the trusted source pin, scope/ruleset/content/profile, expected previous state/log-head, and externally protected event/store/member/authority minima. A fresh connection-bound proof authorizes full-state reads only for explicit trusted replica policy; ordinary PLAYER subscription is insufficient. The server's actual configured owner/device and current role must be pinned, not inferred from an incoming claimed host bit. For profile2, require the real persisted current authority tuple plus current PLAYER+AUTHORITY_CANDIDATE. A receiver proof requires reviewed replica authorization; choose PLAYER+REPLICA reuse or a new explicit ReadReplica operation before implementation. Every manifest/chunk/progress/final result reloads current durable policy and fences changes.

The storage export must capture state, exact profile/pin, revision/event/authority/member frontier, current separately validated membership digest and log head in one read transaction through the sole owner. Add a narrow immutable export port; do not expose raw connection/write access. Journal segments must include the complete closed Store transition sequence, not EventBatch alone: Prepare/Claim/Resume/OutboxAck may change request binding, hold or authority metadata without advancing EventSequence. Include base/result digests, exact revision succession and previous/head hashes. If the requested prefix has been pruned or its base hash disagrees, return a closed GapRequiresSnapshot; never omit entries and label the result synchronized.

No incoming membership snapshot initializes roles or advances local trust. Initial sync requires separately admitted current policy on both peers. Membership-frontier mismatch closes/fences until explicit trusted policy synchronization exists. Automatic policy sync needs a reviewed signed transition history/import seam; accepted current-state CAS alone does not supply that evidence.

## Phase D: staged semantic replica installation

Bulk-verify/1 remains opaque. New sync transfer descriptors must bind document kind/profile/schema/implementation pin, full snapshot or journal base/result hashes, scope/policy, all protected minima, exact total/count/digest and the authenticated session/source. Proposed hard caps: one transfer, <=1MiB semantic document,<=128 ordered8KiB chunks, fixed bounded staging file,<=256 journal transitions,5s idle/30s absolute transfer deadline. Shared structural/allocation budgets must reach every nested semantic decoder before allocation; the existing independent default canonical limits cannot be advertised as negotiated heap enforcement. Reject unknown compression/segmentation/schema. Delete only the exact owned staging artifact on timeout/failure.

Use a separate read-only ReplicaStore mode/profile behind the same foreground repository owner, with no economic commit, authority claim, activity or offline tick APIs. Restore into a new temporary replica database; validate the complete typed Store snapshot and every mirror/reference/request/outcome/hold, compare protected minima and source identity, replay exact typed newer journal transitions, and verify the result hash. Recheck current proof/policy at the final local commit/activation cut. Atomically activate only the verified replica view while preserving the old valid view on failure. A replica activation receipt confirms that local replica transaction only; it is not a strategic DurableAck, quorum result, native save checkpoint or authorization to become an authority. Never install an arbitrary SQLite file, silently recreate missing history or copy remote runtime grants.

Crash tests must cover staging, validation, replay, precommit/postcommit activation and lost final receipt, with real SQLite storage refusal/sync failure where applicable. Reordered/duplicate chunks, unknown records, stale base hash, below-known minima, wrong source/profile, policy revocation during transfer and partial journal cannot publish a view. Reconnect resumes only by a new authenticated descriptor/challenge and a declared exact retry policy; retaining an old proof/transfer as active is prohibited.
