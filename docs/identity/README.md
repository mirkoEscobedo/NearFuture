# Account and device policy

`nf-identity` implements scoped admission decisions and owner-private key storage. The composed node does not expose an identity/transport handler or grant operational roles. Founders in tests are disposable generated identities, not production credentials. `nf-store` implements the public membership compare-and-swap port; issue acceptance needs its actual restart, stale-frontier and crash evidence together with this policy.

An account authorizes device keys. Roles are independent: Player=1, Moderator=2, AuthorityCandidate=4, Replica=8, Archive=16, Relay=32, Worker=64. Masks must be nonzero subsets of 127. Player admits Economic/Chat; Moderator admits Administration; Worker admits Worker work. Candidate status does not itself select an authority; contributed compute never supplies a role. The explicitly selected local founder is the owner. Owner invitations may grant the seven roles; moderators may invite only Player and may revoke non-owner devices. Accounts may rotate/revoke their own devices. No invitation changes the owner or an existing account's roles.

Invitations pin universe/history, issuer account, recipient account/device IDs and public keys, authenticated-peer binding, explicit role mask, random invitation ID, expiry Unix seconds, issuer membership revision and reuse policy. The current policy supports one use; reusable invitations explicitly reject. Redemption verifies issuer membership/role policy, current issuer signature and possession of both recipient keys. It stores the consumed ID and entire new account/device grant in one next snapshot. Expiry is exclusive: `now >= expires_at` rejects. The caller supplies trusted authority time; client clocks are not authoritative. A future issuer revision cannot be admitted against older membership.

Protected admission checks exact universe/history, durable membership revision at least the caller's required frontier, proof frontier exactly current, known non-revoked device, account ownership, registered peer equal to the peer authenticated by the caller's transport, fresh expected challenge and strict device signature. The caller must issue/consume each challenge once and supply its authenticated peer bytes; this library neither authenticates a socket nor manages nonce replay caches. Merely copying a proof or save cannot mint account/device authority. Existing wire schema admission remains separate and insufficient for authorization.

Revocation and rotation signatures include scope and current membership frontier. Device rotation requires the current account key and possession of the replacement device key. Account rotation requires both old and new account keys; AccountId, ownership and roles remain stable. Old device signatures fail after rotation, old account signatures cannot manage subsequent rotation, and stale-frontier mutations reject. Account rotation intentionally retains currently authorized devices; revoke those explicitly when a device is compromised. The immutable public snapshot persists account keys, devices, revocation flags and consumed invitation IDs together. The application shell publishes the result only after SQLite CAS succeeds; conflict or ambiguous persistence returns an error.

# Keys and recovery

Account/device seeds and opaque IDs use maintained getrandom 0.4.3 OS entropy. Owned seeds and private record buffers use zeroize 1.9.0; standard maintained Ed25519 and SHA-256 are reused. Secrets are neither Clone nor serializable/Debug-readable. No seed is passed to a subprocess, game save, invitation, diagnostic or SQLite membership blob. Zeroization is best-effort memory hygiene, not a promise that every compiler, crash dump, page file or privileged observer is controlled.

The vault root must canonicalize outside the caller's selected existing game-save root. It creates new private storage explicitly and refuses accidental overwrite. Original identity records bind IDs, public keys and seeds with a corruption checksum; damaged/missing state returns MissingLocalState without generating replacement keys. New identity creation is a separate explicit action and cannot restore the old account or assets without a new authorized policy decision.

Before publishing a signed key rotation, stage the new key in an immutable private file and sync it. After a durable membership change, `load_membership_keys` selects secrets using trusted persisted public identity. An uncommitted staged key grants nothing; original identity loading remains stable. Failed staging or missing selected key fails closed. A crash may leave an inert staged file or require explicit lost-key handling; there is no cross-file/database atomic replacement claim. Staged files contain private seeds and stay outside saves.

Windows storage uses fixed trusted `private-acl.ps1` source, fixed PowerShell executable and separate literal arguments; user paths/keys are never concatenated into shell code. The helper imports the platform security module explicitly, refuses reparse points, installs a protected DACL with exactly one FullControl allow rule for the current owner, then independently reads the owner and all explicit/inherited rules before any secret write. File ACLs are validated on every load. The hidden owned helper has a five-second timeout and is reaped after cancellation. This source-build profile requires the trusted helper at its compiled source path; packaged deployment must ship/locate trusted helper code or refuse storage. Windows privileges and malicious code running as the same OS account remain outside this boundary.

Linux private modes are 0700 directories / 0600 files with owner UID checked against `/proc/self`; symlinks and relaxed modes reject. Other Unix platforms without that owner-inspection facility fail closed. Actual Windows ACL tests pass. Linux mode code/tests await an observed Linux run; source inspection does not certify them.

Lost account key recovery is refused in the existing history. A community may make an explicit new-history fork/recovery policy decision in a later operator boundary. This library performs no same-history impersonation, administrator key replacement, silent asset reassignment or automatic history merge. Unknown or unverifiable identities cannot perform protected operations.

IPC reuse uses only `create_private_blob`, `read_private_blob` and `remove_private_blob`: immutable create-new files with safe 1–64 byte ASCII alphanumeric/underscore/hyphen names, a `blob-` prefix that cannot address key files, <=4096 opaque payload bytes, private access checks and corruption checks. The caller owns returned secret bytes and must redact them; identity implements no session-token schema, port publication, expiry, socket authentication or stale rendezvous recovery.
