# Local SQLite persistence profile v1

`nf-store` implements local single-authority storage for the private kernel domain-7 codec. It persists an admitted frontier before returning `Accepted` and returns a privately constructed `DurableAck` only after SQLite commits the complete settlement. The crate does not authenticate callers, register kernel payloads on public IPC, publish outbox effects, or provide consensus. `QuorumCommitPort` is a future driver interface; its existence supplies no quorum evidence.

The host must supply an owned local disk directory with reliable filesystem sync and locking. UNC and Windows device namespace paths are rejected; mapped-drive locality remains a host precondition. One connection owns the writer, uses `SQLITE_OPEN_NO_MUTEX`, and verifies `journal_mode=DELETE`, `synchronous=EXTRA`, `locking_mode=EXCLUSIVE`, foreign keys enabled and trusted schema disabled. A second writer receives bounded lock errors. Runtime limits include a 256 MiB database, 2 MiB SQLite values, 1 MiB closed state/action blobs, 4096 retained request bindings, 64 reservations, 256 outbox entries and a checkpoint after each 128 store transitions. Capacity exhaustion produces backpressure or a bounded error before success.

The exact maintained dependencies are rusqlite 0.32.1 and bundled libsqlite3-sys 0.30.1 / SQLite 3.46.0. WAL is disabled. The [SQLite WAL reset defect](https://sqlite.org/wal.html) announced in March 2026 affects older WAL implementations; the chosen rollback journal profile avoids that affected mode. An eventual dependency update must retain the verified journal policy and repeat the storage gates. SQLite describes EXTRA's additional directory synchronization in its [synchronous pragma documentation](https://sqlite.org/pragma.html#pragma_synchronous). Those settings rely on the operating system and storage device honoring sync, as described in [atomic commit](https://sqlite.org/atomiccommit.html).

# Atomic records and recovery

A settlement transaction writes the recorded kernel batch, the complete next world, aggregate revisions, provider draws/cooldowns, every terminal request outcome, released reservations and derived outbox records together. No provider or random generator runs during replay. `prepare` stores the exact frontier, full intent and bound device, including pending reservations. `query` verifies the full retained binding and intent digest; `query_bound` exposes only status and binding digest after exact principal/device/scope matching. Its caller must authenticate and authorize those identities. On an uncertain submission the caller queries the same retained request ID before attempting another prepare. Reusing an ID for different intent or device fails closed.

The v1 schema has ten STRICT tables in `crates/nf-store/src/schema.rs`. SQL counters are fixed-width big-endian blobs so the complete u64 range retains lexical order. Private snapshot codecs use explicit little-endian lengths/counters, fixed typed IDs, ordered collections and strict presence/trailing checks. The `NF-STORE-1` state codec embeds the kernel's closed snapshot/frontier/intent bytes. Membership uses its separate closed identity codec, never private signing seeds. SQLite storage bytes and journal hashes do not authenticate a remote sender.

`application_id`, `user_version`, exact table definitions and absence of unversioned triggers/views/user indexes form the migration scaffold. Only v1 is supported; there is no automatic migration from an unknown schema. Unsupported/corrupt existing files return errors and are preserved. Opening never silently initializes an empty history. Initialization uses explicit `create_new`; backup also refuses overwrite.

Recovery validates SQLite integrity, scope and all caller-known frontiers, then verifies snapshot/state hashes and a bounded consecutive journal hash chain. It replays recorded transitions and compares the final world and all materialized mirrors. Compaction retains bound request outcomes, current provider state, pending frontier/reservations and undelivered outbox. The immutable snapshot value remains unchanged when later transactions commit. SHA-256 consistency checks detect corruption; an attacker able to rewrite all local database contents and checksums is outside this unauthenticated local consistency check.

SQLite's backup API captures world state and separately versioned public membership in one consistent backup. `KnownFrontiers` includes event sequence, store revision and optional membership revision. Restore must receive the caller's latest known minima; a known revocation cannot be rolled back merely because world event sequence is unchanged. The host remains responsible for protecting and retaining those minima outside a replaced backup.

# Observed evidence and remaining gate

On Windows, `cargo test --offline --locked -p nf-store` exercises real SQLite restart, checkpoint/replay, request conflicts, reservations, outbox retention, backup minima and public membership CAS. Six actual owned-child process kills surround transaction start, writes, commit and acknowledgement. The parent verifies the child has terminated, reopens the actual database and checks pending versus committed state; it never substitutes a simulated database. Child ownership and finite deadlines prevent leaked workers.

A genuine SQLite page quota forces `SQLITE_FULL`; no success is returned and rollback retains the prior state/binding. Explicit hooks test pre-commit rollback and post-commit uncertainty/quarantine. Hooks do not constitute an observed filesystem sync failure. A Windows journal handle opened without delete sharing was actually held before commit, but SQLite still returned a successful acknowledgement; that experiment does not establish commit refusal and is not counted as the failure gate.

**Issue #9 remains open:** actual filesystem `fsync`/`FlushFileBuffers` or commit I/O refusal has not yet been safely observed in this Windows environment. Power-loss/device-cache durability has not been tested. A maintained Linux `strace` syscall injector is a possible additional CI gate, using an owned pre-created database and only the exact child executable. [The official strace manual](https://man7.org/linux/man-pages/man1/strace.1.html) documents syscall injection and `--kill-on-exit` for child containment. The implemented Linux-only target is `NF_STORE_REQUIRE_SYNC_FAULT=1 cargo test --offline --locked -p nf-store --test fsync_failure -- --nocapture`. It invokes the maintained injector with `--kill-on-exit`, has a 30-second owned-tracer deadline, caps trace input at 1 MiB, requires an actual SQLite-file sync EIO marked INJECTED, and reopens the original pending binding after no acknowledgement. Windows compiles zero tests in this target. The Linux gate has not run here and is not completion evidence.

Strict checks are `cargo clippy --offline --locked -p nf-store --all-targets -- -D warnings` and `cargo fmt -p nf-store --check`. The signed identity policy integration test, `identity_policy`, uses generated disposable identities and real protected local vaults: one-use admission persists atomically, replay and stale CAS fail after restart, revocation prevents backup rollback, and a staged device rotation survives another restart with the previous key rejected. No game was launched, no game JAR copied, and no network SQLite/history merge was introduced.
