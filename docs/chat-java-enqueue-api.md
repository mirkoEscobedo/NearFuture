# Public Java owner-local Chat enqueue API

`ChatEnqueueClient` submits one outstanding Chat command through an already mutually authenticated CONTROL session. The caller supplies nonzero 16-byte request and original IDs and canonical UTF-8 text of 1..2048 bytes. Account, device, universe and history come from the session; the trusted local owner allocates the message ID and per-sender sequence, signs the original and retains it in the outbox. Exact original retries return the retained Pending or Delivered status. See [the owner-local enqueue contract](chat-ipc-local-enqueue.md).

The client uses the closed Chat enqueue profile 4 and a 4096-byte frame ceiling, reduced by negotiated limits. Before reserving its outstanding slot, it checks the encoded command against negotiated nesting, collection and charged decoded-byte limits. This descriptor preflight does not authenticate or authorize a command. Reply admission uses the existing negotiated decoder, validates the closed status shape and matches runtime, request, principal, scope, original and canonical text. The session fence is checked before and after construction or parsing; stale sessions and invalid replies cannot complete the command. A valid completion returns an immutable `ChatOutgoingValue` and releases the slot.

The Java result is an authenticated local report, not independent device-signature authority. The real CLI/Java test separately verifies the signature in Rust. It exercises the public `enqueue`/`accept` methods against `serve-chat-command`, checks current membership and unchanged store frontiers, reopens durable Pending revision 1 and retries under a fresh node/session without changing the original bytes or SQL files. That whole physical case passed in 31.29 seconds with the original deadlines. The later preflight change was qualified separately; the physical case was not repeated for that change.

Seven independent caller-control groups passed: input bounds, one outstanding command, current fence, reply/profile/correlation, negotiated depth, charged decoded-byte limits and the collection boundary. These controls activate real mutual-authentication transcripts locally; they do not claim sockets or device signature verification. Existing wire boundary, policy and auth-isolation regression classes also passed after the shared decoder refactor. The `chatEnqueueClientTest` task attaches the seven groups to ordinary `:ipc:check`; the physical test remains an explicit opt-in requiring the independently built Java classpath. These results qualify the listed local slices, not a fresh whole-workspace or game test run.

This API adds no network delivery pump, presence, moderation, retention policy, game callback or UI. Existing [two-peer delivery](chat-peer-delivery.md) and [permitted history](chat-peer-history.md) have their own scope and evidence. Chat issue #25 remains open for the remaining shared-feature and real-game acceptance criteria. Delivery does not imply permanent availability when no online peer or archive bridges sessions.
