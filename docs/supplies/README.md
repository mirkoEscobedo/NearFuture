# Supplies vault and provenance ledger

This library implements [issue #27](https://github.com/mirkoEscobedo/NearFuture/issues/27)'s asset boundary. `nf_kernel::supplies` defines bounded amounts, policy, origin, operation and query types; `nf_store::supplies::SuppliesStore` authenticates requests and persists their decisions. A host explicitly selects and opens this separate SQLite profile. The implementation does not select a production host policy automatically.

Balances are keyed by account, supplies content, trust class and lineage. Available, reserved, pending, externalized, minted and burned are unsigned 64-bit integers with checked arithmetic. Each partition obeys `available + reserved + pending + externalized + burned = minted`. Canonical, cooperative-audited and sandbox origins remain separate even when the content identifier matches. Available stock can be issued, reserved or burned. Pending and externalized fields remain zero in this issue's profile; offer release/settlement and native inventory transfers belong to #28, #29 and #30.

A selected `SuppliesPolicy` contains universe, history, ruleset digest and explicit issuance/burn rules. Each rule binds the authorized account, supplies content, exact origin, closed reason and positive per-operation maximum. There are at most 64 combined rules, and at least one issuer. The only supported content is `SUPPLIES_CONTENT = [0x53; 32]`; reasons are `AuthorityGrant` and `AuthorityDestruction`. The policy digest binds every field. Client inventory declarations do not mint stock.

Every operation and owner-only balance/status query requires a fresh signed, one-use challenge bound to its exact intent and current membership. Issuance and authority burn also require membership administration permission; reservation and queries require economic permission. The authorization lifetime remains five seconds. Query account and history permissions are checked before reading outcomes. Requests do not register a new wire capability; these are public library APIs for the trusted host.

Successful effects and global request/operation bindings commit in one immediate SQLite transaction. Exact retries retain the original revision and outcome. A different request for the same economic operation records an alias without a second effect. Changed terms under either identifier conflict. A positive, admitted reservation or authority burn with insufficient available stock also commits a terminal decision. That decision advances the journal revision without moving assets or creating a balance row. Its identifier cannot become spendable after later funding, and authenticated status reports its original operation, revision and `InsufficientAvailable` reason.

Authorization, scope, policy, unsupported content, zero amount, conflicting identifier, ticket replay, precommit expiry and infrastructure errors do not become insufficient-stock decisions. An expiry observed after commit or an uncertain commit error can coexist with a durable decision. Recover with an admissible reopen and fresh authenticated status; uncertain commits quarantine the current handle.

The SQLite `user_version` is 4. Unsupported profiles refuse without automatic migration; existing storage profiles remain separate. Replay checks journal order, policy, original and aliased request bindings, accepted balance effects, and whether the preceding balance actually justified each insufficient-stock decision. The policy/intent domains remain version 2. Operations, request bindings and balance partitions are each bounded at 4096 entries. Logical checkpointing preserves all deduplication evidence and is not physical garbage collection.

The signed test fixture explicitly selects universe `[1; 16]`, history `[2; 16]`, ruleset `[3; 32]`, canonical lineage `[4; 32]`, generated issuer/beneficiary identities, `AuthorityGrant`/`AuthorityDestruction`, and maximum 1000 per operation. Property tests additionally select all three trust classes and separate lineages; the integer boundary test explicitly selects maximum `u64::MAX`. These are synthetic test policies, not a production configuration.

Residual trust remains in the selected host/policy and local storage authority. Replay consistency is not Byzantine issuance certification. The caller must retain known monotonic frontiers independently of a restored database to detect a semantically valid stale backup. Owned-worker crash tests stop before the public issue call or after its actual return before the wrapper acknowledgment; they do not prove in-transaction crash or power-loss durability. No native game or save acceptance is implied.
